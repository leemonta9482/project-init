# 01 · 협업 모드 (여럿이 함께할 때)

> 전제: `00_방법론_원리.md`. 이 문서는 **여러 사람이 참여할 때** 추가되는 규칙만 다룹니다.
> 핵심: **경계를 사람 사이에 긋고, 그 경계를 파일로 자동 강제한다.**

---

## 1. 역할 구조

| 역할 | 책임 | 권한 |
|------|------|------|
| **총괄/PM (Owner)** | 설계(spec/plan), 계약·인프라, 최종 승인 | 전 영역 + self-merge |
| **영역 담당자** N명 | 각자 `{{AREA}}` 구현 | 자기 영역 |

원칙:

- **설계 권한은 PM에 집중** — 무엇을 왜 만들지는 PM이 spec/plan으로 확정.
- **담당자는 구현자** — 확정된 plan을 자기 영역에서 실행.
- **공유 인프라/계약은 PM 전담** — 담당자는 직접 안 만짐(필요 시 이슈로 요청).

---

## 2. 경계 3중 강제

같은 경계를 세 겹으로 건다. (원리 1 + 2)

### 겹 1 — `CODEOWNERS` (자동 배정)

```
{{AREA_PATH_A}}/    {{AREA_OWNER_A}}
{{AREA_PATH_B}}/    {{AREA_OWNER_B}}
{{SHARED_PATH}}/    {{OWNER_HANDLE}}
```

→ 변경 제안이 특정 경로를 건드리면 그 소유자가 **필수 리뷰어로 자동 배정**. 승인 없이 머지 불가.

### 겹 2 — 영역별 `CLAUDE.md` (규칙 명문화)

각 영역 파일이 그 영역만의 스택·계층 책임·금지사항을 담음. (템플릿: `CLAUDE.area.md`)

### 겹 3 — "타 영역 수정 금지" (명시적 금지)

- 각 영역 `CLAUDE.md`에 "다른 영역 디렉토리 수정 금지 (필요 시 이슈)" 명문화.
- 타 영역이 필요하면 **코드로 침범하지 않고 이슈로 요청**.

> 왜 세 겹? CODEOWNERS는 *막지만* 이유를 모르고, CLAUDE.md는 *이유를 주지만* 못 막는다.
> 겹치면 **막고 + 이해시킨다.**

## 3. 승인 게이트 = 리뷰 (개인 모드와의 최대 차이)

머지 전에 **사람 리뷰가 필수**. 리뷰 매트릭스를 문서로 고정:

| 변경 영역 | 리뷰자 |
|-----------|--------|
| `{{AREA_PATH_A}}` | `{{AREA_OWNER_A}}` |
| `{{AREA_PATH_B}}` | `{{AREA_OWNER_B}}` |
| 공유 인프라·계약·문서 | PM self-merge (Owner) |
| 긴급 핫픽스 | PM self-merge + 사후 워크스루 |

### 리뷰 받는 쪽의 강령

- **맹종 금지**: "네 알겠습니다"로 무조건 수용하지 않는다. 이해 안 되면 코멘트로 질문.
- **방어 금지**: 근거 있는 지적은 받아들인다. 리뷰는 통과 의례가 아니라 기술 검증.
- **반영은 추가 커밋으로** — 이력이 squash로 정리되므로 force push 금지.

---

## 4. 교차 영역 협의 — 계약 소유권

두 영역이 만나는 지점(예: 클라이언트↔서버)에서 **계약이 두 곳에 생기지 않게** 한다.

규칙:

- **계약(스키마/API 응답)의 소유자를 한쪽으로 못박는다** (보통 제공하는 쪽 = 서버).
- 소비하는 쪽은 계약을 **임의 변환 금지** — 형태를 바꿔야 하면 제공 쪽을 바꾸고 계약 문서(`docs/API` 등)에 반영.
  - (소비 쪽에서 맞추면 계약이 두 곳에 생겨 어긋난다.)
- 계약 변경 시:
  - 변경 제안에 **BREAKING CHANGE 명시**
  - 상대 담당자와 **사전 협의**
  - `feat(api):` 같은 **양쪽 영향 scope** 사용

### additive 우선

새 필드는 **기존 불변 + 신규만 추가(additive)** 로 만들어, 소비 측이 아직 안 써도 안 깨지게 →
두 영역의 배포 시점을 분리할 수 있다.

## 5. 전체 작업 사이클

```
[PM]   brainstorming → spec 커밋
[PM]   writing-plans → plan 커밋 (Task 1~N)
[PM]   이슈 생성 → 담당자 할당 (spec·plan 링크 첨부)
        │
[담당] 이슈 수령 → spec/plan 정독 → 코드베이스 정합성 점검
[담당] feature/ 브랜치 → Task별 TDD(RED→GREEN) → Task별 커밋
[담당] 로컬 게이트(lint·test) 통과 → 변경 제안(MR/PR) 생성
        │
[리뷰] 리뷰 → 코멘트
[담당] 추가 커밋으로 반영
[리뷰] 승인 → squash merge
        │
[[계약 변경 시]] 계약 배포 먼저 → 그다음 코드 머지 (lockstep, 원리 5)
[CI]   기본 브랜치 머지 → 자동 배포
```

### 구현자 실전 규율 (권장)

- **구현 전 정합성 점검**: plan이 참조하는 함수·헬퍼·import가 실제 존재하는지 선검증 → 런타임 실패 선차단.
- **plan 이탈 시 멈추고 질문**: plan과 코드가 어긋나면 임의 수정하지 말고 **이슈 댓글로 PM에게 질문 → 승인 후 진행**.
- **spec 요구 vs plan 누락**: spec이 요구한 검증이 plan에 빠졌으면 무단 추가 말고 질문 대상으로.

## 6. 협업 모드 요약

| 항목 | 방식 |
|------|------|
| 경계 | 사람 사이 (영역별 담당) |
| 경계 강제 | CODEOWNERS(자동) + 영역 CLAUDE.md(규칙) + 타영역 금지(명시) |
| 설계 권한 | PM 집중 (spec/plan) |
| 승인 게이트 | 리뷰 필수 |
| 교차 지점 | 계약 = 제공 측 소유, 계약 문서 단일화, BREAKING CHANGE 협의 |
| 작업 단위 | 이슈 1개 → 브랜치 1개 → 변경 제안 1개 |
| 소통 | 이슈 댓글(1차) → PM 직접(2차) |
